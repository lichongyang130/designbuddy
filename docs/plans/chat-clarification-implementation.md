# 聊天确认卡片（10.png）

日期：2026-10-15

## 范围

按用户上传的 10.png 实现对话底部确认卡片，不更改共享左侧栏、首页、社区作品和编辑器布局。

- 白色圆角卡片、14px 标题/选项、数字徽标、浅灰选中行、行尾箭头。
- 问题页码、上一题/下一题、关闭按钮、“其他补充”输入、右下角圆形提交按钮。
- 每组 1–4 个问题，每题 2–4 个选项，支持选择加补充或仅自定义补充。
- 任一问题尚未回答时不可提交；只选择、翻页、刷新、关闭都不会继续发送 AI 请求。
- 答案、补充、所在问题页在原任务 localStorage 中持久化；关闭后可恢复，不默认选择答案。
- 确认后将原始任务（含原附件/上下文）与确认答案共同传给既有聊天或生成接口。后续网页修改保留已确认的需求。
- 真实等待状态为“等待你的回答 / 确认后继续”，不是伪造的持续思考。
- 键盘可操作选项，标题/分组/控件有可访问名称；窄屏不产生横向溢出，长卡片可滚动。

## 接入方式与边界

1. 对“帮我做一个UI”这类首轮、缺少形态的 UI 需求做保守的本地前置确认。明确网页/首页/React 等已有具体目标的请求不被统一强制打断。这不是通用自然语言意图识别器。
2. 在线对话系统提示规定：仅在关键缺失信息会实质影响结果时，模型可返回整个 `designbuddy-clarification` fenced JSON 块。客户端完成流读取后严格验证题数、选项数、ID、长度和重复项，再显示卡片。模型是否主动澄清取决于所配置服务对协议的遵循，普通回答仍正常流式显示。
3. 结构化数据不作为原始 JSON 显示；非法确认格式报错且可重试，不继续执行。存储损坏也不造成页面崩溃或自动发送。
4. 原“需要确认后执行”的 `window.confirm` 已替换为同样的卡片，必须明确选择“确认发送”并点击提交。需求澄清不是网络授权，两者不会相互绕过；“仅本地”仍完全不调用 AI。
5. 既有项目生成器只接受网页文件。选择小程序、未确定平台或先梳理需求时进入对话讨论，绝不将 HTML 预览冒充原生应用/小程序发布。刷新和后续追问保留讨论路径。
6. 这不提供模型工具执行、支付/发布审批或通用后台任务引擎；确认后仍调用原 `/api/chat` 或 `/api/generation`，需要用户配置可用的 AI 服务。
