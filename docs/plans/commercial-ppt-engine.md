# 商业级 PPT 智能制作引擎实施方案

日期：2026-10-19  
状态：保留最初提案作为完整蓝图，不是功能完成清单。2026-10-19 已落地首个 P0/P1 生成里程碑，实际范围、测试和未完成项见 [首版实施与验收记录](../commercial-ppt-engine.md)。下文现状审计描述提案时的源码，不代表实施后的状态；P2 及后续项目未提前计为完成。

## 1. 产品定位与核心决策

将 PPT 定义为一个**可持续编辑、资料可追溯、有版本与交付门禁的核心办公技能**，而不是聊天附件生成器。

用户可以从首页自然语言、技能中心、演示专家进入同一份演示项目：输入需求或上传资料 → 查看/调整故事线 → 生成页面 → 修改单页或全局主题 → 查看质检 → 下载交付包。

核心决策：

1. 保留并增强现有 `slides.compose` 编译能力与 `slides.inspect` 检查能力，不重写一套平行插件系统。
2. 在其上新增演示项目与工作流层；用结构化文稿作为唯一业务源，不让模型输出可执行 JS、XML、任意绘图代码。
3. 第一版采用一个受约束的编排器，分阶段调用研究、策划、设计、评审工具。先不做多个自主 Agent 并行互聊。
4. 编辑器、PPTX、PDF、缩略图来自同一份解析后的布局模型。浏览器编辑预览不能冒充 PowerPoint 的真实渲染。
5. 区分“执行完成”“草稿可下载”“自动检查通过”“人工确认交付”。文件生成成功不是商业合格。

## 2. 当前源码：可复用与缺口

| 现有模块 | 代码位置 | 当前能力与边界 |
|---|---|---|
| 可编辑生成 | `server/skills/pptx-deck.ts`、`pptx-theme.ts` | 已有严格 JSON、16:9、主题、文本/形状、柱状/折线原生图表、备注和来源文字；六种页面类型，不是商业叙事生成器 |
| PPT 技能 | `shared/skillRuntime.ts`、`server/skills/executors.ts` | `slides.compose` 支持 TXT/MD/DOCX/JSON；文本输入主要为确定性分页。`slides.inspect` 支持安全读取旧 PPTX、结构/令牌提取 |
| 渲染 | `server/skills/pptx-render.ts` | 使用本地 LibreOffice Kit 生成逐页 JPEG、联系表与 ZIP。现有链路并非独立 PDF 交付，也不认证视觉合格 |
| 任务与下载 | `server/skills/service.ts` | SQLite 持久化、owner 隔离、队列、取消、成果哈希、taskId、提交幂等；不能直接当作支持完整 PPT 恢复的工作流引擎 |
| 技能规划 | `server/skills/planner.ts`、`plan-store.ts` | 根据需求与文件元数据选择一个真实技能；明确不读取正文、不执行多步骤研究。不能把它包装成“商业策划 Agent” |
| 前台工作台 | `frontend/workspace/SkillWorkbench.tsx`、`SmartSkillPlanner.tsx` | 已有授权、提交、状态与成果入口；需增加演示文稿专用编辑界面 |
| 资料处理 | `server/skills/docx-structure.ts`、`pdf.ts`、`pdf-ocr.ts`、`table-*.ts` | 有可复用的解析/计算底座，但各自有格式、页数、公式和安全限制，尚不是通用多资料融合管道 |
| 专家与首页路由 | `frontend/workspace/expertCatalog.ts`、`shared/expertRouting.ts` | 已有演示专家和任务接入；专家规范不等于自主后台执行能力 |
| Agent 外壳 | 例如 `server/agent/runtime.ts` | 该文件的 `run()` 目前直接返回完成与空工具列表，不能将其作为已经具备多 Agent 编排的依据 |

已有 `docs/plans/pptx-skill-evolution.md` 对 PPT 底座作过专门说明；本方案是其产品化与商业质量升级，而非从零引入 PptxGenJS。

### 必须先处理的工程约束

当前通用技能服务包括：单输入文件 ≤2MB、默认执行超时 45 秒、并发上限 2；单次成果连同执行回执最多 10 项、合计 ≤10MB；用户相关存储配额约 100MB，另有全局配额。非 OCR 的排队/运行任务在服务重启后会被标为失败，不会自动断点续跑。

当前 PPT 渲染器内部的转换超时可达 90 秒，与外层默认 45 秒限制存在需要统一的时间预算。不能只改一个数值：应把解析、模型规划、编译、渲染、检查拆成有检查点的阶段，分别设置资源限制、取消与重试策略。

现有渲染说明还记录了中文字体缺失和 WOFF2 不能替代 LibreOffice 所需字体的问题。首轮必须检查实际部署字体、字形覆盖与授权，并把生产渲染依赖纳入发布镜像/安装包；只在开发依赖里存在渲染器不等于生产环境可用。

## 3. 推荐架构

```text
首页 / 技能中心 / 演示专家 / PPT 工作区
                  │
       Presentation Workflow（项目、版本、权限）
                  │
  ┌───────────────┼─────────────────────┐
资料解析与事实库   故事线与逐页策划      品牌/素材库
  └───────────────┼─────────────────────┘
                  │
          PresentationSpec（结构化文稿）
                  │
       布局求解器 → ResolvedLayout（几何与测量结果）
                  │
  ┌───────────────┼─────────────────────┐
编辑器预览    PptxGenJS 编译器     规则与数据检查
                  │
        LibreOffice → PDF / 逐页图片
                  │
    渲染检查 → 有界局部修复 → 再编译/再渲染
                  │
        版本化交付包 + 质检报告 + 人工确认
```

### 技能与 Agent 的分工

- `slides.compose`：保持确定性编译职责，兼容旧输入，按版本演进 schema。
- `slides.inspect`：保留安全导入、结构提取、渲染证据职责，不承诺无损编辑任意旧 PPT。
- 建议新增 `slides.create`、`slides.revise` 工作流入口：前者将需求和资料变成可编译文稿，后者将修改意图变成经过验证的补丁。名称为拟议合同，不是现有 API。
- Planner：识别受众、目的、页数/时长，生成叙事大纲与每页结论。
- Researcher：整理用户资料中的事实、引用、冲突；外网研究是独立可选权限，未接搜索服务时不得声称已调研。
- Designer：只选择受支持主题、布局、视觉组件和素材引用。
- Data analyst：选择字段、图表与公式；实际计算由确定性代码完成。
- Reviewer：提供逻辑与表达建议；其意见与规则检查结果分开保存，不自行授予“事实正确”或“交付通过”。

角色说明文件约束调用行为，但真正的执行顺序、超时、工具白名单和失败处理由代码强制执行。文件正文属于不可信数据，不能改变系统规则、索取密钥或授予新权限。

## 4. 一份真正可编辑、可追溯的文稿模型

建议分成三层，而不是直接保存一堆页面坐标：

1. **SourceBundle**：原文件哈希、解析版本、段落/页码/表格单元格位置、OCR 置信信息。
2. **PresentationSpec**：故事线、页面结论、布局意图、主题、图表/素材引用、演讲备注、稳定 slideId/elementId。
3. **ResolvedLayout**：引擎计算后的坐标、文本框、实际字体、测量结果、组件边界，用于预览、编译与检测。

示意（不是可直接提交到现有编译器的 schema）：

```json
{
  "schemaVersion": 2,
  "presentationId": "...",
  "versionId": "...",
  "parentVersionId": "...",
  "brief": {
    "scenario": "business-report",
    "audience": "management",
    "language": "zh-CN",
    "targetSlides": 12
  },
  "themeRef": { "id": "corporate-light", "version": 1 },
  "slides": [{
    "slideId": "s-04",
    "layout": "chart-with-takeaway",
    "title": "华东区域贡献主要收入增量",
    "claimIds": ["claim-18"],
    "elements": [{
      "elementId": "e-04-chart",
      "kind": "chart",
      "datasetRef": "dataset-03",
      "transformRefs": ["transform-07"],
      "chartType": "bar",
      "sourceRefs": ["source-02:Sheet1!B2:E8"]
    }],
    "speakerNotes": "说明统计口径和期间。"
  }]
}
```

数据集需另行记录数值、单位、币种、时间范围、空值策略和计算过程，不能只放一个来源名称字符串。事实库区分“用户材料主张”“代码核算结果”“用户确认的假设”“外部来源主张”；有引用不代表内容已证实为真。

模型产出的 schema 必须经过白名单校验、引用完整性检查和预算限制；无效响应可有限重试，但不能退回执行模型生成的任意代码。

### 局部修改与版本

“修改第 4 页”先解析成 `{baseVersionId, slideId, operations}`，只允许修改目标范围；服务端校验基础版本，避免覆盖别的编辑。

- 每次提交生成不可变新版本，保留父版本和修改原因。
- 单页修改应保持其他页面的文稿内容与布局不变；通过 IR 哈希与渲染对比测试，而不是要求整个 PPTX 二进制不变。
- PPTX 是含共享主题、关系和媒体的压缩包，首版允许重新打包整份文件。承诺“只修改目标页内容”，不承诺只重写一个 ZIP 文件项。
- 全局主题修改需要重新计算受影响页面、重新渲染与质检。
- 编译和渲染缓存以内容、主题、布局引擎、字体及渲染器版本共同寻址，不能跨字体版本误用旧预览。
- 旧 PPT 第一版只做提取、重建和主题参考，不承诺任意母版、动画、复杂图形的无损往返编辑。

## 5. 商业设计、数据与素材

### 内容场景和视觉主题分开

首版三类叙事模板：商业汇报、融资路演、数据分析。首批视觉主题：高端咨询、企业商务、深色科技；后续再扩展杂志视觉。

融资模板可以提供市场/竞品/财务章节，但材料缺失时必须标注待补充，不能捏造 TAM、增长率、客户或经营指标。

### 布局组件

在现有六类页面上，优先补齐：执行摘要、目录/章节页、左右对比、原生表格、流程/路线图、图文组合、行动结论。每类布局提供多个密度变体，不做所有内容都塞进同一种卡片。

主题统一管理：画幅、字体族与回退策略、配色、字号层级、网格、间距、页码、页脚、Logo 安全区。布局引擎负责换行、测量、对齐和留白，而不是让模型临时猜坐标。

### 图表

第一批强化原生柱状、折线图，并补原生表格与 KPI；再验证饼/环形、堆积等。瀑布、漏斗、复杂组合图必须逐项验证生成库与目标软件表现，不先承诺全部原生可编辑。

数据核算必须保存输入范围和转换步骤，明确单位/期间/分母、舍入和缺失值；避免汇总行重复统计。现有公式引擎仅按其白名单复用，不能声称完整 Excel 兼容。

### 素材

首版支持上传 Logo、产品截图与图片、内置授权清晰的图标和确定性图示。后续可接素材搜索与图片生成，但必须有单独权限、成本和许可说明。

素材库保存 owner、内容哈希、来源与许可、尺寸和使用页。不能让模型返回任意 URL 后由服务端随意抓取；远程下载需单独安全网关，防止 SSRF、恶意 SVG、超大图及内容类型伪装。图片内的文字无法因此变成可编辑文本，不能把整页图片包装成“完全可编辑 PPT”。

## 6. 前台：一个工作区，多个入口

新增 `PresentationWorkspace`，而非把通用技能表单无限加长：

- 左侧：缩略图、章节、排序和页面问题标记。
- 中间：大画布，标题/正文/图表可选中；提供真实渲染预览切换。
- 右侧：内容、布局、图表数据、来源、品牌设置。
- 底部：真实阶段进度、事件和失败重试，不展示虚构的百分比。
- 顶部：文稿版本、另存版本、交付检查、导出。
- 主要操作：重写本页、更换布局、把文本转图表、补充章节、压缩页数、统一主题。

所有入口关联同一个 taskId/presentationId；对话中的“第 4 页”绑定当时的版本和稳定页 ID。没有成功上传或解析的附件不得显示“已阅读”。

首版以“模型生成默认方案 + 可选确认”为主，只有缺少关键事实、数据口径或权限时才追问。对自动生成/付费模型调用提供一次清晰的执行授权，不把每个内部步骤都变成确认弹窗。

## 7. 贴合本仓库的模块与接口

建议目录是职责边界，不要求一次创建所有空文件：

```text
shared/presentation.ts                 # schema、版本、补丁、阶段与质检合同
skills/ppt/SKILL.md                     # 供技能消费方读取的工作规范
skills/ppt/agents/*.md                  # 受约束角色规范
server/skills/presentation/
  orchestrator.ts                       # 任务阶段、检查点、重试与取消
  sources.ts                            # 多源统一提取与事实/数据引用
  planner.ts                            # 故事线与逐页意图
  schema.ts                             # 严格验证与旧版适配
  store.ts                              # owner、项目、版本、素材、工件清单
  layouts/                              # 组件与文本测量
  themes/                               # 品牌令牌与视觉主题
  quality.ts                            # 文件/布局/数据规则
  repair.ts                             # 白名单内有界修复
  exports.ts                            # PPTX、PDF、图片与报告关联
server/skills/pptx-deck.ts              # 复用并重构现有编译器
server/skills/pptx-inspect.ts           # 复用安全检查
server/skills/pptx-render.ts            # 复用并扩展 PDF/图片渲染
frontend/workspace/presentation/        # 编辑工作区、缩略图、来源与版本
```

注册继续使用 `shared/skillRuntime.ts`、runtime catalog 和现有执行器；`SKILL.md` 不是注册替代品，增加文件本身不会使技能自动可执行。需明确加载与版本关系。

拟议 API：在现有 Node API 中扩展，不新增示例中的 Next.js `app/api` 目录。

| 接口 | 职责 |
|---|---|
| `POST /api/presentations` | 创建需求、来源引用及任务，返回项目与 job ID |
| `GET /api/presentations/:id` | owner 校验后的项目、文稿与版本信息 |
| `GET /api/presentations/:id/jobs/:jobId` | 持久化阶段和事件，首版可复用轮询 |
| `POST /api/presentations/:id/revisions` | 带 baseVersionId、requestId 的受限修改 |
| `POST /api/presentations/:id/exports` | 针对不可变版本请求编译、渲染与交付检查 |
| `POST /api/presentations/:id/jobs/:jobId/cancel` | 取消当前阶段并阻止旧结果提交 |
| `POST /api/presentations/:id/jobs/:jobId/retry` | 从允许恢复的失败阶段重新执行 |

这些是新接口建议；工件下载尽量沿用已有授权下载能力。编排器通过明确的内部服务方法提交子任务，不通过“自己请求自己的 HTTP 接口”绕过身份与权限。

复用现有队列的 owner、幂等和工件合同，同时补项目工作流状态；不要在一次 45 秒 worker 里串完所有模型与渲染步骤。模型凭据只在授权调用时使用，不写入任务 JSON、版本、日志或执行回执。恢复时若没有有效授权/凭据，应进入等待授权，而非声称自动恢复成功。

成果存储先抽象 artifact store：小型文本/报告可以继续 SQLite，较大 PDF/图片包通过内容寻址本地存储，后续再接对象存储。按 owner 配额、任务版本、保留策略和孤立文件回收治理，不能只删除原有配额判断。首版预览包与 manifest 控制成果数量，不直接为 25 页塞入 25 条顶层成果记录。

## 8. 自动质检与商业交付门禁

质量报告必须包含检查器/规则版本、执行范围、证据、未检查项与具体 slideId/elementId。建议四个维度独立报告，而不是一个掩盖错误的总分：

| 维度 | 首版检查内容 | 不能冒充的结论 |
|---|---|---|
| 文件有效性 | ZIP/XML、必要部件、关系、媒体存在、页数、可渲染、原生对象与工作簿结构 | 不等于已在全部 PowerPoint/Keynote 版本验收 |
| 内容质量 | 大纲完整、重复、结论与证据对应、受众与任务覆盖；模型建议单列 | 不等于论证或事实必然正确 |
| 视觉质量 | 对象边界、文本测量、受保护区域重叠、字号、对比度、字体/缺字、图片和渲染异常 | 文本框在画布内不等于文字不溢出；合理覆盖不应全部报错 |
| 数据质量 | 单元格/范围引用、转换链、单位与期间、图表数值、未知/冲突标记 | 来源存在不等于来源真实或已独立核验 |

严重问题阻止“正式交付”状态；用户可下载明确标识“未通过/未完成检查”的草稿。渲染器缺失、关键字体缺失、关键数据冲突未处理均不能获得正式通过。全部自动检查通过后仍保留人工确认，视觉模型评审不能替代规则或人工签收。

自动修复最多建议两轮：调整已允许的布局/密度、扩展文本区域、重排或分拆页面；不能靠把字号无限缩小、删关键事实、改图表数值或偷偷换统计口径“修好”。涉及内容删改必须可比较并获用户确认，失败后停在需要人工处理状态。

交付包关联同一任务与版本，至少包括：PPTX、PDF、逐页预览 ZIP/manifest、演讲备注、来源与数据说明、质量报告。编辑源 JSON 可用于备份/复用，但企业策略可限制包含原始材料的完整导出。

## 9. 分期实施与退出标准

| 阶段 | 开发内容 | 验收后才进入下一阶段 |
|---|---|---|
| P0 底座加固 | 复测现有 PPT 生成/渲染；中文字体与许可；渲染器生产打包；统一资源预算；定义 schema、版本和 artifact store 迁移 | 固定样稿在目标环境可重现；无中文方框；资源超限与渲染失败不误报通过 |
| P1 核心商业生成闭环 | 自然语言 → 正文提取 → 大纲 → 结构化文稿 → 编译 → 基础检查；商业汇报/路演/数据分析三类故事线；基础主题、原生图表/表格、备注、PDF | 能用真实材料生成 8–25 页可编辑文稿，图表值一致；缺失信息明确标记；模型不可用时明确失败或转入手工结构化输入，不伪造 AI 策划 |
| P2 编辑与版本 | 专用工作区、单页补丁、主题切换、页序、压缩/扩展、版本比较与恢复 | 修改指定页不改其他页；并发旧版本被拒绝或提示冲突；每个预览与报告对应确切版本 |
| P3 多资料与视觉强化 | 跨文件事实库、PDF/OCR、图片、旧 PPT 提取重建、品牌素材、更多布局/图表、渲染检查与有界修复 | 冲突、OCR 低置信、数据来源可追查；典型溢出/缺字/缺图能发现；无法修复不放行 |
| P4 企业产品化 | 阶段恢复、配额和成本治理、审计、组织品牌包、队列扩展、缓存、批处理、可选外部研究 | 重启/取消/重试不会重复扣费或覆盖版本；跨用户隔离与恶意文件测试通过 |

基础安全、owner 隔离、幂等和失败恢复合同从 P0/P1 就实现；P4 扩展企业规模，不是到最后才补权限。

第一轮资料范围建议 TXT/MD/DOCX/XLSX/CSV，复用已有解析合同；按每份 ≤2MB、最多 5 份、总计 ≤10MB 起步，生成 8–25 页。具体格式仍遵守各解析器更严的限制，后续经压测再放宽。PDF/扫描件/旧 PPT 与复杂图像理解分批扩展，不直接把聊天附件支持列表当成 PPT 已读懂的格式。

## 10. 验收集与推进建议

建立固定黄金样稿和故障样稿，至少覆盖：中文商业汇报、带财务假设的融资演示、真实 Excel 数据分析、长标题/密集正文、中英混排、品牌 Logo、图片缺失、字体缺失、资料冲突、OCR 错误、恶意 OOXML、服务重启、重复提交与取消。

测试分层：

- 单元：schema/补丁、文本测量、图表数据、来源和布局规则。
- 集成：解析 → 文稿 → PPTX → PDF/图片 → 检查的真实链路，不能只测试 ZIP 中存在 slide XML。
- 页面稳定性：单页修改前后，非目标页的 IR 与渲染结果比较；全局主题变更使用另一组预期。
- 安全与资源：跨 owner 访问、压缩炸弹、宏/外链、图片解码、超时、配额、重复请求与中断恢复。
- 产品：首页、技能中心、专家页三入口到同一项目，编辑、失败重试和下载全过程。
- 目标软件人工验收：约定版本的 PowerPoint、Keynote 或其他目标软件中真实打开并编辑文本、图表、表格；不能用 LibreOffice 或 XML 测试代替未进行的软件验收。

**推荐推进顺序：先 P0 + P1 打通可信的商业生成闭环，再 P2 做持续编辑；后续补齐 P3/P4。** 不建议同时建设完整多 Agent 平台、自由画布、全格式无损导入和复杂图表引擎，否则最容易得到展示页面很多、实际交付不稳定的产品。

建议首个验收成果是三套使用许可明确、数据可核对的样稿，而不只是接口和截图：商业汇报、融资路演、数据分析各一套，附编辑源、PPTX、PDF、预览和质检记录。只有它们在约定环境通过门禁，才把功能标记为可商业交付。
