# Word 商业级输出增强：源码核对与分期实施方案 V1

日期：2026-10-19  
状态：用户已批准W0＋W1＋W2，现已接入受限首批 `document.create`；实际功能、测试和未完成项见[实施记录](../word-pro-v1.md)。下文仍为原分期蓝图，不全部视为已实现。  
需求：从内容规划、专业排版、真实分页到有限修复和文件交付，形成独立于 PPT 的专业 Word 生成流程。

## 1. 结论与优先级

接受用户提出的八模块方向，但不一次性承诺所有文档类型、任意旧 Word 无损编辑、全自动事实核查或跨软件版式一致。

首批建议批准 **W0 + W1 + W2**：

- W0：建立真实渲染基线、内容保全清单和质量门槛。
- W1：商业报告、项目方案两类独立结构规则，原生 DOCX 排版与同源 PDF/全页预览。
- W2：对可可靠定位的问题执行最多两轮确定性排版修复，每轮重新渲染，保留前后证据。

首批只做新建文档；读取旧稿作为来源不等于旧稿原位编辑，不承诺任意旧稿无损往返。

首批先用来源锁定的结构化内容证明排版闭环，不把助手编排案例当成后台 AI 自主规划验收。AI 规划/专业写作在 W3 独立接入、授权和验收；不是把已有摘要技能冒充全文生成。

核心成功标准不是“导出了 DOCX”，也不是“页面更少”，而是：**内容未丢、原生结构可编辑、最终文件真的渲染过、检查范围可解释、修复可追踪、未知问题没有被包装成通过。**

## 2. 已核实的源码起点

本节来自本轮源码阅读，不是本轮重新运行功能测试的结果。

| 实际模块 | 已有能力 | 不能据此宣称 |
|---|---|---|
| `server/skills/executors.ts` 的 `document.format` | 依非空段落/显式标题生成 DOCX；另行生成 PDF | PDF 是 DOCX 的真实分页结果；已有智能分页或 AI 写作 |
| `server/skills/source-text.ts` | TXT/MD 与 DOCX 主正文文字提取，来源段落编号 | 原件页码、完整表格语义、图片/批注/页眉页脚保全 |
| `server/skills/docx-structure.ts` | 受限正文结构、表格/合并、图片、部分样式/分节与安全 HTML 预览 | HTML 是 Word 渲染；支持任意域/文本框/修订或复杂旧稿编辑 |
| `document.summarize` | 独立、显式授权的正文语义摘要 | 完整报告生成、全文重写、事实已核验 |
| `scripts/render-docx-libreoffice-reference.mjs` | 实际 DOCX → LibreOffice 页图与哈希记录 | 已进入生成服务；已经有分页检测与修复；Microsoft Word 验收 |
| `server/skills/pptx-render.ts` | 实际 PPTX 的本地渲染、PDF/页图、受限资源与临时文件处理 | 不改造即可当通用 Word 渲染器；Word 页数预先已知 |
| `server/skills/office.ts`、`fonts.ts` | Office 包安全校验、授权字体相关基础能力 | 所有 Word OOXML 特征均支持；所有字体均允许嵌入 |
| `shared/skillRuntime.ts`、`server/skills/{contracts,executors,service,worker}.ts` | 技能目录、参数白名单、执行映射、所有者隔离、任务/文件持久化、资源限制 | 新建 `SKILL.md` 即会加载新技能；所有技能已有可恢复检查点 |

### 必须先改正的同源问题

当前 `document.format` 通过 `writePDF(sections)` 与 `Packer.toBuffer(doc)` 分别生成 PDF 和 DOCX。二者虽来自相同段落，但不是同一个排版引擎的结果，不能以该 PDF 证明 DOCX 的分页、表格位置或页眉页脚正确。

Word Pro 的交付 PDF 和页图必须来自**最终 DOCX 字节**。报告记录最终 DOCX、PDF、页图及内容清单的 SHA-256、引擎/字体版本、实际页数。旧整理技能可保留，但不得继续把它的独立 PDF 标成 DOCX 真实预览。

Linux 当前已验证参考工具采用 LibreOffice Kit 的 WebAssembly 后端，不是桌面原生 LibreOffice，也不是 Microsoft Word；对外文案需保留区别。

## 3. 架构：共享基础设施，不共享分页逻辑

建议逻辑分层：

```text
已授权来源 → 安全解析 / 来源定位 / 原始事实清单
                         ↓
                 Word 内容与章节计划
                         ↓
             WordSpec（结构化内容，不是代码）
                         ↓
        Word 专属样式、分节、表格、图片与分页规则
                         ↓
                 DOCX → 本地真实渲染
                         ↓
         结构检查 + PDF 文本/几何检查 + 待人工检查项
                         ↓
          有限规则修复 → 新 DOCX → 再渲染与全篇回归
                         ↓
            DOCX + 同源 PDF + 页图 + 质量/修复记录
```

### 可与 PPT 共享

安全归档/XML/图片校验、来源 ID 与哈希、授权字体来源、素材使用声明、数值字段绑定、服务端模型调用与用量记录、任务所有者隔离、输出存储、报告信封、临时目录清理。

先抽取经两条路径验证的公共接口，不先进行大范围框架重写。复用字体来源不代表复用 PPT 固定字号；复用来源工具不代表把正文段落号当成表格单元格来源。

### Word 必须独立

A4 等纸张与分节、正文样式、标题层级、段落流、孤行控制、标题保护、表格重复表头/跨页、题注、目录与页码域、页眉页脚、长文参考文献与附录。

不移植 PPT 固定画布坐标、每页四条要点、每 N 页放大图等规则。Word 的实际页数由渲染产生，不把模型估计页数当作物理页数。

## 4. 八模块对应的第一批边界

| 模块 | 首批 W0–W2 | 后续 |
|---|---|---|
| 内容规划 | 显式章节树、原始事实/表格/来源清单、缺失材料记录 | W3：有来源约束的 AI 章节计划与审阅 |
| 专业写作 | 输入内容保全，不自动改写事实、生成业绩或补填负责人 | W3：计划后写作、术语/重复/矛盾提示，人工核验 |
| 版式设计 | 原生标题/正文/表格/题注、封面、页眉页脚、页码；两种文档类型 | 品牌定制、更多类型、复杂分节 |
| 智能分页 | 标题与后文保持、孤行属性、表头重复、可靠定位后的有限修复 | 复杂跨页/混排的规则扩展与兼容性验证 |
| 图表与表格 | 原生数据表、列宽/单位/口径/来源说明；已有授权图片的受限布局 | 原生 Word 图表、流程/组织图编辑能力单独验证 |
| 模板与风格 | 商业报告与项目方案使用不同结构要求，而非仅换颜色 | 公文、论文、合同、制度等专用规则与专业审查 |
| 质量检查 | 实际渲染、内容覆盖、结构/几何信号、有限修复、未知项显式列出 | 像素/视觉模型审阅、经人工校准的评分 |
| 文件交付 | 最终 DOCX、同源 PDF、全页预览、来源/质量/修复记录 | 持久版本工作区、自然语言局部修改、另存模板 |

合同/规范性文件的结构检查不等于法律有效性审查；公文或论文模板也不能在缺少目标单位/期刊要求时宣称合规。

## 5. W0：真实基线与内容保全

### 基准文档

建议先建立仓库可公开的合成/助手编排案例：

1. 商业报告：封面、摘要、三级标题、长段落、多个表格、风险与建议、来源附录。
2. 项目方案：目标、范围/非范围、交付物、建议关卡、资源待确认、风险与验收条件。
3. 失败夹具：页尾孤立标题、超宽表格、过高图片、较长不可拆行、目录字段、显式空白页、缺字及重复文本。

可沿用已有领导决策案例的已公开材料制作内容对照，但不得编造预算、日期或把建议试点写成已批准。这是排版基准，不是外部模型质量证据。

### 内容清单

每个可交付节点具有稳定 `nodeId`、类型、文本/单元格内容、来源引用、数据范围和计算说明。原输入、WordSpec、每轮 DOCX 与 PDF 分别记录哈希。

修复前后比较内容与数据绑定清单。允许移动、换行、改变列宽或经过批准的样式参数；不允许删除正文、删行、缩写数字、重算口径或把内容隐藏后声称“已解决溢出”。

DOCX 书签/段落标记可辅助关联节点，但不假设这些 ID 自动保留到 PDF。PDF 文本匹配存在重复、连字或断行歧义时标记 `unresolved`，不自动定位或修复。

### 基础资源预算

先测量现有 Worker 默认 45 秒、256MB JS 堆与通用 10MB 交付上限；Word 渲染和修复不可直接套用这些默认值，也不能直接复制 PPT 300 秒后声称足够。

确定并测试单文档字符/节点/表格/图片/页数、单轮渲染、整任务期限、输出和存储配额；超限明确失败，不靠截断内容达标。若新增可恢复任务，需单独设计持久阶段和资源配额，不冒用当前仅给 OCR/PPT 的恢复逻辑。

## 6. W1：原生生成与同源交付

### 库与目录建议

优先沿用已安装的 TypeScript `docx@9.5.1`，不因方案示意而引入第二套 Python 服务。库不支持的功能应先做可验证原型，不默认它支持所有 Word 图表/图形。

拟新增（尚不存在完整实现）：

```text
shared/wordDocument.ts                  # 版本化需求/WordSpec/报告协议
server/skills/word-pro/
  SKILL.md                             # 人工/Agent 工作规范，不是自动加载器
  schema.ts / sources.ts               # 严格解析、来源与受限输入
  styles.ts / templates.ts             # Word 专属令牌和类型规则
  generate.ts                          # 原生 DOCX
  render.ts                            # 同 DOCX 的 PDF/页图与引擎回执
  inspect.ts / repair.ts                # 可靠信号、有限修复与停止条件
  pipeline.ts                          # 阶段编排、版本与交付
frontend/workspace/WordComposer.tsx     # 本地准备、用途/模板/授权
```

需要同时接入实际目录、参数校验、执行映射、服务超时/上传/存储约束及前台结果组件；不能只加目录与提示词。新技能 ID 暂拟 `document.create`，落地时先检查冲突；旧 `document.format`、`document.structure`、`document.summarize` 保留原合同。

### 文档模型

内容节点与版式参数分开；章节、段落、表格、图片、题注和来源均用声明式白名单结构。模型不输出任意 OOXML、Python/JS、文件路径或渲染命令。

原生表格必须包含表头含义、单位/数据范围、来源及存在计算时的公式说明；文字数字不得为排版而被悄悄改值。跨页优先重复表头和允许合理分行，不对所有表格一刀切“不跨页”，以免制造大块空白。

图片保持比例；证据图默认完整显示，截图不能为美观隐藏关键区域。装饰图裁切应保留裁切记录。原文件可能包含 EXIF 或裁切外内容，沿用规范化和隐私提示。

### 目录与页码

原生 TOC/PAGE 等字段不等于字段缓存已刷新。先验证当前 LibreOffice 后端的字段更新、目录页码与 DOCX 回存能力。

若字段更新导致最终 DOCX 字节变化，应以更新后的最终 DOCX 重新导出 PDF 和页图，重新绑定哈希。若无法可靠回存，明确标注“目录待目标 Word 刷新”，不得把目录正确列为自动通过，也不得硬编码容易失效的目录页码。

不能用 `document.structure` 的受限解析器强行重新解析含 TOC 等不支持字段的生成文档，再通过放宽其输入安全规则解决。需为自身生成合同建立独立的结构验证，保留上传文件的安全边界。

### 可编辑性边界

正文、标题、表格、页眉页脚与题注保持原生。图片作为独立图像对象，不把整页拍成图片。

“原生 Word 图表”需要实际 OOXML 图表、数据绑定/嵌入工作簿及安全校验，并在目标 Word 编辑验证后单独宣布完成。图像图表不能标成原生可编辑图表；图片流程图也不能标成可逐节点编辑。

## 7. W2：可验证的检查与有限修复

### 检查依据分层

1. **DOCX 结构**：标题跳级、必填章节、样式引用、表头/列宽、字体声明、字段与图片关系、内容清单。
2. **真实 PDF 文本/几何**：实际页数、内容覆盖、页尾标题候选、可映射文字的边界、重复页眉页脚与页码信号。
3. **页图/视觉**：空白候选、大块空白、图片/表格外观等；像素稀疏不等于无内容，大块空白可能是封面或合法分节。
4. **人工或另行授权的视觉模型**：整体观感、复杂重叠、语义一致、Office 差异。未执行时保持待审，不以结构检查替代。

“未发现”只适用于实际检查范围；未覆盖项用 `not-evaluated`，不默认 `passed`。正文 PDF 中缺失可能由提取问题引起，应区分“疑似提取遗漏”和已证实的 DOCX 内容丢失；无法判断时阻止商业确认并人工复核。

### 首批自动动作白名单

| 问题与证据 | 允许动作 | 禁止/需确认 |
|---|---|---|
| 可靠映射的页尾标题且后文在下一页 | 标题 keep-next、适度段距调整 | 删除标题或移动到错误章节 |
| 列宽总和已证实超过可用版心 | 在可读阈值内按内容重分列宽，复验全部单元格 | 删列/删行、随意缩字、变更纸张方向而不确认 |
| 跨页表格缺重复表头 | 设置首行重复并再渲染 | 认为出现重复表头就证明整表无问题 |
| 已知图片框超出可用版心 | 等比例缩小到受限框内，检查题注和分页 | 拉伸、证据图裁切、用低清替换原图 |
| 孤行/段落分离的可验证候选 | 段落孤行属性、受限段距/keep 调整 | 强制所有长段不拆分、无条件删除空段/分节 |

正文最小字号是模板约束，不能通过把全文缩成小字解决问题。拆表、转横向分节、删摘要、改变引用、法律条款或实质文字属于需要确认的修改。

### 次数与停止条件

初始生成后最多两轮修复，即最多三次完整渲染；这是拟定策略，需要资源基准验证后设定生产限制。若期限不足，不启动下一轮。

每轮记录问题 ID、节点/页码、定位置信度、规则版本、参数变更、内容清单对比、前后文件哈希、已消失/新增/仍存在的问题。不只检查原来出错的一页，因为修复会改变后续分页。

关键内容丢失、严重溢出、不可解析、内容清单改变或修复产生更严重问题时，不交付“通过”状态。可回退上一安全版本，但仍标明未解决问题；达上限即停止，不进行无限循环或追加未授权模型调用。

### 拟议报告信封（示意，不是本次检测结果）

```json
{
  "schemaVersion": 1,
  "documentType": "business-report",
  "inputSHA256": "<actual input hash>",
  "finalDocxSHA256": "<actual final docx hash>",
  "finalPdfSHA256": "<actual PDF hash>",
  "checks": {
    "headingHierarchy": { "status": "not-evaluated", "method": null },
    "contentCoverage": { "status": "not-evaluated", "method": null },
    "tableWidth": { "status": "not-evaluated", "method": null },
    "tocPageNumbers": { "status": "not-evaluated", "method": null },
    "renderedVisualReview": { "status": "required", "method": null }
  },
  "issues": [],
  "repairRounds": [],
  "score": { "weightsVersion": "proposed-1", "calibrated": false, "weightedScore": null },
  "releaseStatus": "needs-human-review",
  "commercialApproval": false
}
```

真实报告不得保存占位哈希；真实问题包括 severity、检测依据、节点/实际页码（无法定位则为 null）、定位状态、建议动作和是否允许自动执行。

## 8. W3 与后续批次

### W3：来源约束的 AI 规划与专业写作

复用模型调用、用量记录和权限框架，不直接复用 PPT 逐页导演协议。Word 计划以章节目的、主张、证据、表格/图示需求和缺失项为单位，避免把长文写成幻灯片要点拼贴。

先审阅章节计划，再写正文；术语、单位、时间范围、数字与引用建立独立清单。来源存在不等于论断受支持；矛盾检测和模型审阅只能给候选问题，不自动“修正”事实。

外发正文需单次明确授权；像素/视觉模型审查需另列图片传输范围和授权。调用上限、失败保留、恢复预算需持久化，不能靠重试任务偷偷增加模型调用。无服务端模型配置明确不可用，不用固定范文替代生成。

### W4：更多类型、图表、局部修改与工作区

- 公文/论文/制度/合同分别建立专业规则，先要求适用标准；不做无依据的“自动合规认证”。
- 原生图表、复杂流程图与混排按编辑能力分级验收。
- 版本历史、局部修改与模板保存使用真实持久存储和所有者隔离，不能仅做按钮或内存预览。
- 锁定内容后“改为董事会风格”只改变授权范围内的结构/排版；重写正文须展示差异并重新检查。
- 外部图像自动生成另有通道、成本和授权边界，不作为 Word 首批的隐含依赖。

## 9. 评分、硬门槛与验收

可沿用用户建议的初始权重：视觉30%、内容25%、结构20%、页面稳定性15%、编辑/兼容性10%。这是产品初始设计，不是标准认证。

在没有人工样本文档校准之前，输出分项检查、覆盖范围和待审项，综合分为 null；不能用模型给出的“95分”替代真实检查，也不能把未检查项排除后展示看似完整的高分。

### 硬门槛

- 文件无法安全重开、缺关键内容、数据不一致、严重可证实溢出 → 不通过。
- 渲染失败、缺字/字体问题未解决、字段页码不可信、定位存在歧义 → 待处理/待审，不自动商业批准。
- 结构/视觉自动检查全绿仍不等于事实、版权、法律或目标 Office 验收通过。

### 分层验收清单

1. 单元：schema 白名单、标题树、表格数据/单位/口径、样式、来源与内容哈希、修复边界及停止条件。
2. 真实导出：DOCX 包结构和原生对象；同 DOCX → PDF/全部页图；最终哈希链；实际字段/字体状态。
3. 修复回归：故意缺陷可被检测，动作与问题匹配；全篇重检；内容不变；无法可靠判断时拒绝自动修复。
4. Worker/API：实际任务执行、超时/取消/资源上限、原子交付、下载字节、外部失败、所有者隔离；新增恢复逻辑单独验收。
5. 浏览器：本地准备与授权、阶段进度、目录/缩略图/PDF预览、真实下载、失败不显示虚假结果、移动端；没有开发完整编辑器时不展示假编辑按钮。
6. 人工：逐页查看所有输出，并用 Microsoft Word/WPS 等目标客户端单独验证目录刷新、分页、表格和可编辑性。记录客户端版本/字体，不把 LibreOffice 结果推广为所有客户端结果。
7. AI：W3 的 mock/助手编排与真实模型基准分开；最终需真实模型、已授权材料和独立人工质量评审。

编写本方案时仅完成源码核对，并未新增执行器或生成新的DOCX/PDF。随后获批的首批实施与测试请看[实施记录](../word-pro-v1.md)；Word/WPS客户端验收仍未完成。历史测试记录按其原有范围解释。
