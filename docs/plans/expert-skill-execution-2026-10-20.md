# 专家与技能调用：从角色提示到实际交付的改造方案

日期：2026-10-20。源码基线：`a010fba`。本轮仅核查源码、提出方案，不修改应用调用逻辑，不宣称执行了真实模型对比或新验收。

## 一、结论：为什么选了专家，感觉没有变化

这个感受有实际依据，但不能说专家现在完全没有作用。

目前专家确实会影响：首轮任务的专业提示、部分对话/网页生成路径，以及文件执行台允许选择的工具范围。**专家本身尚不是一个负责规划、调用、检查和交付的完整执行角色。** 多数情况下，仍是同一套模型接口接收一段不同的任务指导。

| 现状（已核查） | 源码位置 | 用户能感受到的问题 |
| --- | --- | --- |
| 选择专家会生成职责、方法、检查清单，拼入首条用户请求 | `apps/web/src/components/useExpertMatch.ts` 的 `executionBrief`；`shared/expertRouting.ts` 的 `expertExecutionBrief`；`App.tsx` 的 `startProject` | 会影响回答方向，但不能证明实际做了工具处理或检查 |
| 主对话统一走 `/chat`，服务端系统规则明确该聊天没有外部工具；请求没有完整的专家执行配置/版本契约 | `frontend/workspace/api/taskChat.ts`；`server/api/chat.ts` | “以某专家回答”与“由专家执行交付”是两回事 |
| 首轮规范会作为历史继续进入聊天，并非后续完全丢失；但未作为独立、版本化任务角色快照管理 | `TaskConversationPage.tsx` 的 `runReply`、`submit`；`taskConversation.ts` | 多轮修改缺少稳定的任务负责人、交付规则和版本机制 |
| 首页选择技能主要拼入“使用技能：名称”；推荐技能被存为建议 ID | `App.tsx` 的 `skillPrefix`、`suggestedSkillId` | 选中名称不等于实际创建技能运行 |
| “对话”与“文件技能与产物”分开，用户还要切页签、准备文件和确认 | `TaskConversationPage.tsx` 的 tabs 与 `SkillWorkbench` | 做文件任务时，容易先得到文字回答，再手动接工具 |
| 文件技能模型规划目前选择一个真实工具，不是通用多步代理 | `SmartSkillPlanner.tsx`；`server/skills/plan-store.ts` | 单工具路径已有安全闭环，但不会自动做完整跨工序交付 |
| 协作专家主要作为说明拼进同一个提示，未形成独立的协作运行及审查产物 | `useExpertMatch.ts` 的 `collaborators`、`executionBrief` | 显示了多人分工，不代表多位专家实际分别工作 |
| 新增成果页有真实多工序流程，但任务对话未统一调度这些成果流程 | `shared/skillProducts.ts`；`server/api/workflows.ts`；`TaskConversationPage.tsx` | 技能页的整合成果，还没有完整变成专家任务入口的执行能力 |
| 自建专家目前以本地角色/文本职责为主，未绑定后台工具的自建专家在任务页被阻断 | `expertCatalog.ts`；`ExpertsPage.tsx`；`TaskConversationPage.tsx` | 填写能力名称，不会安装执行器或自动取得工具权限 |
| 部分“思考过程”并非服务端实际执行事件：网页分支等待500ms后就写“需求分析完成” | `TaskConversationPage.tsx` 的 `runReply` 网页分支 | 看似有过程，但不能作为专家分析或工具执行证据，应移除 |
| 自动匹配取得的技能信息只保留 ID/名称/输入格式，未保留实时可用性和专家绑定信息 | `useExpertMatch.ts` 的技能目录读取 | 匹配阶段可能推荐当前不可执行或不适合该专家范围的工具；后续服务器仍会阻断，并不是越权执行成功 |

另外，当前通用文字回答转技能的桥接会将部分答案包装为 `ai-content.md`。这只适合明确支持 Markdown 的执行器，**不是通用的PPT/Word/图像/表格结构化输入适配器**。后续不能继续靠改扩展名串接不同 schema。

## 二、产品定义：三个概念各管一件事

- **模型**：负责理解、规划、撰写、按约束生成结构化结果。专家不必各占一个模型账号。
- **专家**：任务负责人，定义专业方法、材料要求、可调用能力、交付结构和验收门槛；对实际结果及限制负责。
- **技能**：真实执行动作，例如解析文档、生成PPTX、计算表格、排版图片、渲染、静态检查。必须有执行器、输入输出和真实运行记录。

推荐链路：

```text
用户目标 + 材料 + 已有选择
    ↓
判断：只咨询 / 需要实际交付
    ↓
确定成果类型 + 一位主责专家
    ↓
核对材料、依赖、预算和已有授权
    ↓
冻结可审阅执行计划
    ↓
专业规划 / 内容整理
    ↓
真实技能 / 现有多工序流程
    ↓
专业检查 + 有限修复 / 人工待复核
    ↓
统一交付区：文件、预览、来源、版本、质量状态
```

普通问答不要强行多专家、多步骤；生成文件的明确任务不要只给聊天答案。

## 三、推荐交互：不再让用户自己拼专家和工具

### 1. 首页只保留三个主要操作

- 输入“我要交付什么”，附材料。
- 默认自动分配主责专家；用户手动指定时优先保留，不静默换人。
- 识别为文件交付时，按钮显示“开始制作”或“查看制作计划”；普通咨询保持“发送”。

不要求每次重复问“咨询还是制作”。明确要求PPTX、DOCX、海报或源码时直接选择相应路径；仅在歧义会导致不同交付时问一个必要问题。现有模型匹配授权不自动扩大为正文外发或付费执行授权。

### 2. 发送前显示一张简短任务卡

示例文案（设计建议，不是执行结果）：

> **主责：演示专家**  
> **目标：可编辑项目汇报PPT**  
> **计划：读取材料 → 规划逐页内容 → 生成PPTX → 真实渲染 → 检查**  
> **需确认：受众/页数中尚未提供的必要项，以及正文外发授权**  
> **当前阻断：若服务器未配置正文模型，说明缺什么，不启动假制作。**

不能把“计划调用”标成“已经调用”。不确定价格时说明按服务商账单计费及目前无法估算，不编数字。

### 3. 结果区直接出现交付，而非再去找技能页

同一个任务里展示：实际产物、预览、缺项、来源、质量检查、版本、下载和“按要求修改”。技术详情中才展开专家/技能 ID、运行 ID、参数和报告。

技能页保留为直接制作与高级工具入口；专家页保留为能力说明和配置入口，不要求用户两边来回切。

## 四、专家如何与8类成果真正绑定

保留既有专家ID和历史；下表是默认责任建议，不是删除现有角色或新建8个模型账号。

| 成果 | 默认主责 | 默认执行路线 | 检查与边界 |
| --- | --- | --- | --- |
| 专业演示 | `slides` | 现有 `slides.create` 内部材料/规划/原生生成/渲染管线 | 来源、可编辑对象、渲染与人工逐页复核；缺AI凭据时阻断。原稿制作/分析场景显式选 `slides.compose/inspect`，不冒充专业AI路径 |
| 专业文档 | `documents` | `document.create`；按任务选择整理/提要/结构提取 | DOCX/PDF同源性、内容完整、分页和人工目标端复核；提要外发另授权 |
| 数据报告 | `data` | 先选合适的数据/关联/公式场景，再调用现有执行器 | 字段、口径、复算、来源；未提供的单位和业务逻辑不猜测 |
| 品牌系统 | `brand` | `brand-delivery`；设计令牌等按场景选择 | 资产一致性、CSS/HTML静态检查和负责人审阅；不做商标权保证 |
| 营销/商品视觉 | `visual` 或实际商品场景的 `product-visual` | `marketing-delivery`、图层编辑、商品适配等明确场景 | 文案、目标尺寸、裁切、权利；没有图像通道时不冒充AI生图 |
| 网页原型 | `web-design`；涉及真实开发时由 `developer` 主责 | `web-delivery`；浏览器复测另作为授权检查步骤 | 区分源码生成、静态检查、实际浏览器检查和上线；不开放未隔离构建 |
| 项目方案 | `product` | `project-delivery`；计划/日程按明确场景选择 | 需求验收覆盖、依赖、待确认项；不虚构负责人/工期或代发通知 |
| 质量检查 | `qa` 或目标文件对应的专业检查角色 | 根据实际文件选HTML/CSS/JS、Office或浏览器检查 | 每一步使用登记允许的执行专家绑定；不能因选了QA就获得所有工具 |

协作角色不应凭空取得全部工具。跨组步骤必须在服务端计划中明确委派给已登记的执行专家，继续校验所有者、工具绑定、授权和额度。不能把主责专家的工具列表无限放大来“解决”跨组调用。

## 五、实现方案：统一任务编排，而不是再加一个专家选择器

### A. 建立服务端专家能力档案

建议字段：`expertId`、`configVersion`、职责、方法、输入要求、成果类型、可用流程、工具约束、输出schema、检查规则、明确不支持项。

工具可用性必须取服务端实时目录，而不是角色文案或浏览器传来的“我会某技能”。档案分开保存：平台硬约束、专业工作规范、用户自定义偏好。用户创建的专家提示不能提升为安全规则或扩大工具权限。

现有 `expertCatalog` 可以继续供前端展示，但不是执行权限的最终来源。

### B. 持久化统一任务与执行计划

建立或扩展统一任务记录，关联而不是替代现有 `SkillRun`、`WorkflowRun`：

- `taskId`、所有者、成果类型。
- 主责专家、档案版本/快照；是否用户锁定。
- 已提供材料与来源引用、缺项、交付要求。
- 计划版本/摘要、步骤依赖、真实输入/输出引用。
- 已确认的操作范围、外发对象、预算/次数上限。
- 各步骤实际运行ID、状态、失败原因、取消状态。
- 当前产物版本、检查状态、人工验收状态。

前端可以展示建议计划，只有服务端验证后的计划才可执行。模型不能自行创造工具ID、路径、输入schema或扩展权限。每一步按实际输入输出校验，适配器必要时显式转换并保存来源关系。

### C. 先复用固定可靠链路，再增加受控规划

1. 确定性路由先处理明确的8类成果与已知场景，直连已有专业管线/配方。
2. 简单任务可直接调用一个现有执行器，不为“专家感”增加多次模型请求。
3. 需要模型规划的任务，只返回符合schema的计划；服务器检查能力、绑定、依赖、版本和许可，再请用户确认必要的外发/付费范围。
4. 首版默认一位主责，必要时加入一位有独立结果的审查角色。复杂任务最多两位协作角色作为建议上限，不默认所有专家轮流回答。
5. 每位实际参与者必须有具体输入、工作项和结果记录；只提供提示时就标为“专业指导”，不能叫“已完成协作”。

### D. 把聊天修改接回同一份真实产物

例如“第三页减少文字”应带上当前演示版本，修改相应内容、重新生成/渲染并复检，产出新版本；不能只回复“已经修改”。未实现某类精细编辑时明确说明，保留原件，不假装原生对象编辑成功。

按工具实际能力逐类建设修改适配器，不承诺现有Word有限修复、PPT管线、图层编辑已经支持统一任意修改。新版本保留父版本、源材料引用及输入/输出哈希，计划或材料变化时撤销旧确认。

### E. 真实状态而不是模拟思考

状态建议：待材料、待确认、规划中、制作中、检查中、需修复、草稿可下载、人工待验收、失败/已取消。

步骤事件来自真实模型请求、技能运行、渲染和报告读取。去掉定时等待后显示“分析完成”的做法；“已选专家”仅表示配置已选择，不表示该专家完成了任务。不展示或编造模型私有推理。

## 六、授权、费用和失败的默认规则

- 本地、无外发的确定性链路可在用户确认计划范围后自动串联，不要求每一步重复点确认。
- 第三方正文、生图、邮件/日历写入、收费操作按现有单次授权或冻结的批次范围执行；新增对象、步骤、材料或明显改变成本时重新确认。
- “仅本地”不调用云端规划/生成，不因为选了专家而绕过。
- 缺模型、工具、许可或隔离环境时阻断对应步骤；可用替代路径要明确征得选择，不能偷偷降级。
- 同一步幂等，重试制作时重新检查依赖产物；失败可保留诊断，不能标记全部成功。
- 模型调用/费用只按提供商实际回报记账，不把估算当账单；限制调用次数、运行时间和产物大小，不无限重试。
- 自建专家可先拥有指导能力；申请工具绑定时由服务器审批允许范围，并展示“仅指导 / 可规划 / 可执行”三种真实状态。不能填写一个技能名称就取得执行权限。

## 七、分阶段实施及可验收成果

| 阶段 | 做什么 | 验收条件 |
| --- | --- | --- |
| 1. 让专家选择产生真实路线差异 | 服务端能力档案/版本；稳定任务角色；区分咨询与交付；任务页直连现有Word、PPT及营销链路；过滤不可用推荐；去掉模拟完成步骤 | 选演示专家并要求PPT时产生真实演示运行，或明确缺配置；不再只返回文字就说做完；旧任务/身份/授权不破坏 |
| 2. 扩展到8类成果 | 统一任务计划与结果区；把已有网页/品牌/项目等配方接到任务入口；模型计划严格校验；跨专家明确委派 | 每类任务至少一个实际样例，实际运行ID、文件、来源、检查报告齐全；不兼容输入明确拒绝 |
| 3. 专业质量与修改闭环 | 独立检查/有限修复；逐类产物版本与修改适配；自建专家绑定与账户同步 | 修改实际反映到新文件，重新渲染/复测；原件可恢复；商业/目标端人工验收单独记录 |

不承诺尚未核算的工期。先做阶段1，以真实任务验证，再扩展，不重做登录页或继续堆专家卡片。

## 八、如何证明“真的起作用”

必须分别测试，不能以角色名称、动画或模型自我评价代替：

1. **有无专家的差异**：同一份材料、同一目标，对照计划、交付结构、实际调用和检查覆盖；不能只比较措辞是否更像专家。
2. **手动锁定**：明确选择的专家不能静默被自动匹配替换；确实无法交付时解释并请求改路线。
3. **工具证据**：每个“已调用/已渲染/已修复”都能对应运行ID及实际文件/报告；检查期间失败不能提前显示完成。
4. **多轮稳定**：刷新、继续追问后仍保留主责档案版本、材料范围、交付目标和当前产物版本。
5. **失败与边界**：缺AI配置、缺材料、格式不支持、未知工具、越权、超预算、取消和重复提交都分别测。
6. **多专家不是装饰**：协作和审查要有独立记录，区分自动硬检查、模型建议和人工判断；没有执行不能出现已完成徽标。
7. **商业差异**：真实任务下比较人工修改耗时、遗漏/事实错误、可编辑性、视觉偏好、费用和失败恢复。尚无样本结果，不宣称提升比例或优于竞品。

## 九、建议结论

**不要继续增加专家数量；先把已有专家变成能选择正确路线、调用真实工具、检查并交付的任务负责人。**

最先验证的任务：一份有来源的项目汇报PPT、一份正式Word报告、一套带实际图片的营销海报。可复用的底层能力已经存在，关键缺口是统一任务编排、专业检查和修改后的同源交付，不是再换一段更长的提示词。

本方案尚未实施。不因此新增采购、部署、外部账号配置或正文外发授权。
