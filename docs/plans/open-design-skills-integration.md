# OpenDesign 244 项技能接入方案（待批准）

日期：2026-10-19。状态：实施建议，尚未开始导入或接入。

## 1. 目标与明确口径

让当前 DesignBuddy 源码具备可追溯、合法分发、按需加载并受控执行的上游设计 Skill 系统，而不是添加 244 条名称或把 SKILL.md 注入聊天后就声称可运行。

基准盘点：网站目录 244 条；本仓库未发现这 244 个原版包的接入证据；旧 `skills/catalog.json` 有 180 条描述；实际 `shared/skillRuntime.ts` 与 `server/skills/executors.ts` 对应 49 项本地技能。盘点时运行接口报告 45 ready、4 unavailable，配置变化后须重新检查。

验收分别统计：

1. **目录覆盖**：244/244 条都有唯一记录、上游来源、需求、许可证审核和处理结论。
2. **源码收录**：逐项报告已合法纳入的完整原版包数量，不能把仅有链接的项算作已导入。
3. **宿主适配**：说明是本机兼容、已适配，还是缺工具/不支持；保留原版与适配层的差异。
4. **可运行**：依赖、账户、凭据与权限实际满足，且有受控执行路径。
5. **已验证**：记录针对固定版本、具体输入与环境的真实运行证据；不等于全面质量保证或商用认证。

“244 条全部可见”可以作为首期硬目标；“244 套源码全部合法可分发、在同一环境全部可运行”必须以逐包审计、授权与依赖验证为前提，不能提前承诺。

## 2. 保留现有系统，不另建一个假技能商城

- `shared/skillRuntime.ts`、`shared/skillPlanning.ts`：当前本地工具定义、计划与结果约定。
- `server/skills/service.ts`：已有所有者隔离、运行记录、任务和成果持久化、配额/幂等/取消等基础。
- `server/skills/skill-permissions.ts`、`server/skills/contracts.ts`：服务端权限和参数校验。
- `server/api/ai.ts`：模型请求、凭据配置和用量处理；扩展时仍不得内置任何密钥。

- 49 项本地工具多数接收单个文件；上游工作流可能接收目标、项目、多个材料并跨多个工具运行，不能伪装成现有单文件执行器。

## 3. 原版文件、版本和许可

### 先全量建账，再决定哪些源码可纳入

244 条逐项记录：网站详情 URL、上游仓库和技能路径、固定 commit、原始名称、中文展示名、任务类型、输入输出、工具要求、许可文件位置、审查日期、审核决定与原因。

同名技能不能合并。使用来源仓库与技能路径生成稳定且唯一的命名空间 ID；原始名称只作显示，不能作为唯一键。索引固定本次 244 项，不因网站日后增加条目而静默改验收分母。

### 不只复制一个 SKILL.md

在允许纳入后，保留原版入口、被引用的 references/scripts/assets、LICENSE/NOTICE 与必要依赖声明。资源闭包须审查：可以复用仓库级共享资源，但不能盲目整库复制，更不能默认把示例中所有外链都当成已包含资源。

原版内容尽量保持原样；本地中文说明、兼容性调整与工具映射放在独立适配元数据中，注明修改和来源。并非每个上游包都能在本宿主原样运行。

### 许可证门禁

- 实际核验仓库、文件及资源的许可，而不只采信网站标签。
- MIT/Apache-2.0 等在确认范围、附带条款与资源许可后纳入。
- CC-BY 等落实署名与具体要求；AGPL、非商业用途、Figma 特定条款、冲突或未确认项进入显式审核，不自动当成可自由商用。
- 不能确认可纳入的项，先保留来源引用、阻断原因与人工处理入口，不复制来源正文或受限资源；不得记成已安装。
- 不承诺 244 个包全部适用同一种分发方式；必要时联系权利人、采取合规分发安排，或经用户批准使用明确标注的自研替代。自研替代不冒充原版。

### 更新与供应链

首次导入与后续更新均固定 commit 与每个文件哈希，不在产品运行时拉 main/latest。导入过程检查路径穿越、符号链接、包大小、异常文件与密钥；不运行生命周期脚本。依赖锁定版本并另审安装步骤。更新先产生内容/依赖/权限/许可差异，审核后启用；运行中的任务始终绑定旧版本，不半途升级。

## 4. 工作流不是单纯的“提示词注入”

目标调用链：

```text
用户目标 + 用户明确选定的项目/材料
→ 候选检索（只读摘要，不把 244 份全文塞入模型）
→ 选择主技能与必要的辅助技能
→ 加载固定版本指令及所需参考文件
→ 检查宿主兼容、工具、材料、权限与预算
→ 展示执行计划和外发范围，等待本次确认
→ 有界模型/工具循环
→ 真实修改或生成文件
→ 构建、浏览器/文件规则校验与人工复核提示
→ 输出成果、来源版本、执行记录与失败边界
```

上游指令是待审查内容，不是授予权限的指令源；不能覆盖系统规则、用户约束或工具网关。只在当前模型/宿主支持可靠的结构化工具调用时启用执行路径，不支持时明确停在准备/说明状态。

拟区分三类模式：

1. **指导型**：研究计划、设计评审、信息架构等。按原版流程产出 Markdown/JSON；需要模型时明确外发授权。生成建议不等于完成真实研究。
2. **项目/工具型**：前端、浏览器验收、PPT 等。调用现有工具或新增受控适配器，必须实际读写/渲染并交付文件。仅文字“已修复”不算成功。
3. **外部环境型**：Figma/Stitch/Penpot、Remotion/HyperFrames、Three.js/CAD 等。只有连接器、账户、软件、许可证及隔离运行环境真正满足后才启用；缺任一项显示具体阻断原因。

模型必须给出可验证工具请求，服务端逐项验证 schema、所有者、项目、文件引用、工具白名单与当前授权。计划不是授权。技能变更、输入变更、版本升级或外发范围扩大时，原确认失效。

## 5. 安全和执行边界

- 项目读取仅限用户明确授权的根目录与材料引用；规范化路径、阻断越界、控制总量，不默认扫描全部源码或上传项目。
- 写入采用预览差异、限定文件、版本检查和可回退的项目快照；只回退本次修改，不能覆盖其他并发编辑。删除文件、改依赖、联网、启动命令和发布另设权限门。
- 本地本身存在文件不等于用户授权读取/外发；源码注释、网页内容和上游 SKILL 不得自动扩权。
- 外部 AI、图像、连接器分别授权；显示数据范围和目标服务，不在日志、Git 或成果中写密钥。
- 明确单次步数、时长、工具调用/模型预算与产物大小上限；超限停止并保留实际进度，不伪装已完成。
- 浏览器/下载网关防 SSRF、危险协议、重定向越界和跨项目数据泄露。
- 任意第三方脚本在建立经过验证的隔离执行环境前默认禁用；不能把普通子进程命名成“沙箱”。隔离环境需限制挂载、环境密钥、网络、CPU/内存/时长及输出路径。
- 重启恢复不能静默重放可能计费或有副作用的外部请求；沿用检查点/幂等原则，无法确认结果时提示人工检查。
- 技能运行不自动发送邮件、发布网站、推 GitHub 或写第三方账户，除非用户明确批准该操作。

## 6. 页面与产品接入

延续当前共享侧栏与技能页，不重做全站。增加“本地工具 / 上游设计工作流”分区，以及分类、来源仓库、许可、可运行性与依赖筛选。

不要用单一 ready 布尔值掩盖不同阶段。独立记录并展示：目录已收录、源码已引入/仅来源链接、许可已审核/待审核、宿主原生兼容/已适配/不支持、依赖就绪/缺失、最近验证通过/失败/未测。

详情显示原版文件、来源版本、依赖、许可、适配差异、实际交付与最近验证证据。用户可以手动选择；自动匹配只提出计划，不下载包、不执行、不默认外发。首期可先手动使用以保证链路可靠，再开启受控推荐。

首页、专家与项目页共用该目录和权限检查；专家档案或推荐理由不能凭空产生执行能力。

旧 180 条目录保留兼容与收藏迁移，但明确为“任务方法/描述”，不混入原版安装数或 49 项本地执行器统计。

## 7. 实施顺序与首批候选

### G0：244 项来源、许可和依赖审计

交付固定索引、依赖/资源闭包清单、许可决定与接入优先级。244 条全部有可解释状态；报告能合法导入的实际数量，不预设它等于 244。无原版下载执行，无模型调用收费。

### G1：加载器、工作流基础与首批 20 项

在 G0 审查通过范围内，引入完整原版包、实现最小必要工具网关和工作流，先完成“手动选择 → 确认 → 执行 → 真实交付 → 验证”的闭环。

以下 20 项是按当前产品重点选出的**候选**，不是已导入或已确认许可证兼容的名单；审计若发现依赖或许可阻断，应先报告再替换，不降低验收要求：

| 方向 | 5 项候选 |
|---|---|
| 前端 | frontend-design、ui-ux-pro-max、baseline-ui、responsive-design、web-component-design |
| 评审 | design-critique、plan-design-review、fixing-accessibility、accessibility、web-design-reviewer |
| 设计系统 | design-system-patterns、ui-design-system、visual-design-foundations、design-token、color-system |
| PPT | pptx-quality-gates、pptx-reference-deck-analysis、pptx-slide-specification、pptx-visual-assets、slide-making-skill |

PPT 必须区分原生可编辑 PPTX、HTML 幻灯片和图像式 PPTX。不能把不同交付格式悄悄互换。复用现有编译、渲染和检查代码时记录适配范围，不改写现有冻结示例冒充新成果。Word 保留现有独立质量规则，不借此次接入暗中扩展为已完成任意旧稿编辑或 AI 写作。

### G2：扩大指导型和通用前端/品牌/研究技能

在已验证框架上按包分批扩大；补自动推荐、参考资料按需加载、任务组合与回归。每批有安装、兼容、依赖、真实验证的单独统计。用户研究技能只能处理获准材料，不声称已招募、访谈或收集真实数据。

### G3：专用环境与外部依赖

按明确需求接入图像、GSAP、Figma/Stitch/Penpot、视频、3D/CAD 等。图像提供商/模型仍未确定，不能代选、自动调用或要求在聊天里粘贴密钥。外部环境按一次一个适配器推进，在实际可用且合规的目标环境验收。

### G4：244 项闭环与升级机制

所有条目都有最终可解释结论；仍受许可证、授权或环境阻断的项明确列出负责人/下一步，不能为了得到“244 全绿”去跳过门禁。提供版本更新差异、旧版本回滚、兼容性报告与维护说明。

各阶段完成并核对后再进入下一批，不在 G0 之前承诺工期、可导入数或全量运行成功率。

## 8. 验收标准

### 对每个“已验证”技能

- 原版来源、commit、文件闭包哈希、许可证材料齐全，适配改动有记录。
- 从 UI 或真实 API 发起一个符合其任务的用例，不只测试生成了字符串或目录卡片。
- 实际生成其声明的格式与文件；需要可编辑对象则检查对象，而不只看扩展名。
- 需要浏览器/渲染/第三方服务的，提供对应真实证据；缺依赖、取消、预算耗尽、权限拒绝与上游失败不能报成功。
- 质量证据明确自动发现项和人工复核项；不能由一次样例推导全面商业质量。

### 对系统整体

- 244 条无遗漏、来源命名空间不冲突、状态和计数可复算。
- 49 项现有本地技能及既有项目、设置、PPT、Word 关键回归不退化。
- 路径越界、提示注入、未授权外发、跨账户、版本变更、并发写入、取消与恢复等安全测试通过。
- 320px 移动端和桌面可用，加载失败能重试，缺依赖不能显示“已运行”。
- 源码、许可文件、测试与实施记录可提交 GitHub；密钥、运行数据库、用户上传和依赖缓存不入 Git。

## 9. 建议批准范围

建议先批准 **G0 + G1：244 项全量建账与审计、原版包加载/受控执行基础、首批 20 项真实闭环**。允许在许可清楚的范围内将原版包与必要参考资料纳入源码；受限项先阻断列明。首批不包括任意第三方脚本无限制运行、付费图像自动调用、外部账号操作或自动发布。

G0 的结果决定后续每批的准确包数量、依赖与工作量。用户批准方案前，不执行导入或安装操作。
