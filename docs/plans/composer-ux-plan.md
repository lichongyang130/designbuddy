# 首页输入区改造方案：从「系统词汇」改成「解决痛点」

> 依据：在 dev server（5173）实跑取到的真实 DOM，不是凭印象。

## 一、现在屏幕上到底是什么

| 位置 | 现在显示的原文 | 问题 |
|---|---|---|
| 输入框右下 | `⌘K 找场景、技能与插件` | 3 个抽象名词 + Mac 快捷键；讲的是**功能**，不是结果 |
| 权限下拉旁 | `按账号设置执行` | 对新人是无信息量的兜底话，等于「反正有个地方配了」 |
| 权限下拉 | `默认权限` / `仅本地 · 不联网` / `需要确认后执行 · 发送前问一次` | 下拉里已写了「不联网」，右边又跟一句解释：一个控件两处说明 |
| 示例行 | `试试` `长文重点摘要` `多份材料合并` `政策条款速读` | 「试试」没有宾语；三个 chip 是**任务名**（功能分类语言），不是用户脑子里的那句话 |
| placeholder | `描述你的想法，例如：制作一个产品介绍PPT…` | 这条其实是全页最清楚的一句，反而最不显眼 |

## 二、为什么「很多用户看不懂」

1. **「试试」没有宾语。** 试什么？chip 上写的是「长文重点摘要」——这是我们自己给任务起的名字，用户脑子里是「我这份 80 页的材料读不完」。
2. **最大的价值被藏起来了。** 点一下 chip 不是填几个字，而是注入一段**结构化需求**（任务目标 / 具体要求 / 工作方式 / 质量与交付要求）。这恰恰是「需求写太短 → 结果平庸」的解药，但界面上一个字都没说。
3. **数据里本来就有痛点文案，只是从没显示出来。** 目录结构是 `分类 → 痛点 → 任务`：
   - 分类：文档整理 / 数据表格 / 会议纪要 / 周报总结 / 汇报PPT / 邮件沟通 / 计划排期
   - **痛点（group）**：材料太多读不完 · 多表对不上数字看不懂 · 工作做了不会总结 · 汇报没有清晰主线 · 项目排期总是延期 ……

   而且当前这 3 个 chip 恰好全都来自同一个 group（「材料太多读不完」）——痛点就在数据里，屏幕上却一个字没有。

## 三、要解决的三个真痛点（按优先级）

- **P1｜不知道怎么把需求说清楚。** 用户打「做个PPT」→ 结果平庸。这是最值得解决的，而示例行本来就是解药。
- **P2｜我的文件、我的内容会不会被传走。** 权限控件就是答案，但现在用「权限 / 默认权限 / 按账号设置执行」这种系统词讲。
- **P3｜冷启动时不知道能拿它干什么。** 输入框 + 空白，没有任何「你能得到什么」。

## 四、方案

### 第一步：减法（你点名要删的两处，零风险）

- 删掉 `HomeComposerSection.tsx:362` 的 `<kbd>⌘K</kbd> 找场景、技能与插件` 整个 hint
- 删掉 `useHomeComposerController.ts:34` 里 `PERMISSION_HINTS` 的 `默认权限: "按账号设置执行"`

**成本：0 测试改动。** 已确认没有任何 spec 断言这两句文案；`默认权限` 时 policy span 为空，CSS 里已有 `.composer-policy:empty` 规则，不会留空位。

### 第二步：「试试」行改造（核心）

**方案 A — 把痛点显示出来（推荐，改动最小）**

```
现在：  试试  [长文重点摘要] [多份材料合并] [政策条款速读] ↻
改后：  材料太多读不完？  [长文重点摘要] [多份材料合并] [政策条款速读] ↻
```

label 从固定的「试试」换成当前这批 chip 所属的 **group（痛点）名**。因为 3 个 chip 本来就来自同一个 group，这个映射是天然成立的，不需要新的排序逻辑。

**方案 B — 把「点一下会发生什么」说出来**

```
不会写长需求？点一下，直接帮你写成完整描述
[长文重点摘要] [多份材料合并] [政策条款速读] ↻
```

**建议 A + B 合并成两行**：

```
材料太多读不完？                                    ← 痛点，会随模式/输入变化
[长文重点摘要] [多份材料合并] [政策条款速读] ↻        ← 点一下就填好完整需求，可再改
```

**方案 C — 最激进（可选）**：一次展示 2 个痛点 × 3 个例子，↻ 改成「换一个困扰」。信息量更大，但首屏更重，不建议先做。

**成本：0 测试改动**（只要保留 `.home-suggestion` 类名、数量 3、以及「换一批」的 aria-label 即可；「试试」这句 label 文本没有任何 spec 断言）。

### 第三步：权限文案改成人话（可选，但建议做）

**必须保持不变**：`<option>` 的 **value**（`默认权限` / `仅本地` / `需要确认后执行`）和 `aria-label="任务权限"` —— 有 10 个 spec 文件靠它们选值和断言，改了会大面积返工。

**可以改的只是显示文案**：

| 现在 | 建议 |
|---|---|
| `仅本地 · 不联网` | `仅本地 · 文件和内容都不上传` |
| `需要确认后执行 · 发送前问一次` | 保留（已经够清楚） |
| `默认权限` | 删掉 hint 后不再有解释，直接留空 |

**成本：1 处断言**（`home.spec.ts:127` 断言 `.composer-policy` 等于「不发送任何 AI 请求，只存在本机」）。另外 `frontend/workspace/i18n.ts` 里 `home.permission.*` 有中英两版，改文案要双语同步。

## 五、成本小结

| 步骤 | 文件 | 测试改动 |
|---|---|---|
| 第一步 减法 | 2 处 | 0 |
| 第二步 试试 → 痛点 | 1 个组件 | 0 |
| 第三步 权限文案 | 1 处文案 + i18n 双语 | 1 句断言 |

## 六、需要你拍板的三件事

1. **「试试」用 A、B，还是 A+B 合并？**（我建议 A+B）
2. **权限显示文案要不要一起改？**（会动 1 处测试断言，但 P2 是真实信任痛点）
3. **⌘K 那句删掉后，要不要在 ＋ 菜单里补一句更口语的入口说明？**（比如「按 ⌘K / Ctrl+K 搜索页面、场景、技能、插件」——把 ⌘ 补成双平台写法，而不是在首屏最显眼的位置挂着）
